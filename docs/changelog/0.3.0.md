# 0.3.0 — Cortex-M7 port + unified capability gating

**Opened:** 2026-06-11 (`0.3.0-dev` after the stable sync) &nbsp;·&nbsp;
**Status:** in development &nbsp;·&nbsp;
**Targets:** adds STM32F767ZI (Nucleo-F767ZI), Cortex-M7

The current development minor. Brings NavHAL to a **second Cortex core** on real
hardware and overhauls how capabilities are gated across the whole tree.

## What's new

### STM32F767ZI / Cortex-M7 port (F7-1 … F7-7)
A full hardware bring-up of the F767, reusing the shared `armv7e-m` arch layer:
- **Board bring-up** framed around the MCU (not just the Nucleo), with an F767
  startup and its **own STM32F767 vector table**.
- **Clock** driver up to **216 MHz** with over-drive mode (F7-3).
- **USART** on the F767ZI (F7-2); **SPI** (`CR2.DS`/`FRXTH` IP) and **I²C**
  (timing-register IP) F7 drivers (F7-6).
- **Flash** map + M7 `flash.c` DSB/NULL fixes (F7-4); verified **FPU / DWT /
  DMA / PWM / hardware CRC** on the F767 (F7-5, F7-6).
- **Polled SDIO** on the STM32F7 SDMMC with a PIL round-trip (async/DMA path
  deferred pending L1-cache validation).
- **On-target CI**: F767 in the **Renode PIL** matrix + on-target build and
  white-box GPIO/TIMER/UART suites; host SIL suites for clock + flash KV-store.

### Capability matrix docs
- A full **silicon + driver** capability matrix (`docs/capabilities/`) covering
  F401RE, ATmega328P and F767ZI, including undriven silicon and core blocks.

### Unified capability gating (Linux `autoconf`-style)
The three overlapping gating spellings were collapsed onto one:
- Guards now key off a single family, **`NAVHAL_CONFIG_DRV_*`** (a 1:1 mirror of
  Kconfig), which the build **force-includes** (`-include navhal_target.h`) into
  every translation unit — ambient, tested with `#if`.
- The legacy **`_*_ENABLED`** spelling and the `navhal_port_config.h` bridge were
  **removed**; **`NAVHAL_HAS_*`** is retained only as deprecated aliases for
  out-of-tree consumers (guarded by an alias-equivalence conformance test).
- Kconfig existence guards tightened so nothing is offered that cannot run:
  DMA-backed UART/I²C options gated to Cortex-M4 (where the backend exists),
  and the `DRV_CRC` label corrected (software fallback on AVR).
- Dropped the dead `#define CORTEX_M4` from samples/tests (arch is build-selected).

### Memory Protection Unit driver
- A new **ARMv7-M MPU** driver (`hal_mpu`), shared by Cortex-M4/M7, gated on
  `NAVHAL_CONFIG_DRV_MPU`. Region count is read at runtime from
  `MPU_TYPE.DREGION` (8 on M4, 16 on M7); pure encoders keep validation off the
  context-switch fast path (`hal_mpu_encode` + `hal_mpu_apply`).

### NAVIXSM-F401RE board
- A custom STM32F401RE flight-controller board joins the tree
  (`src/board/navixsmf401re/`, `BOARD_NAVIXSM_F401RE`). It carries the parts the
  Nucleo leaves off — a 32.768 kHz crystal and USB on a connector — which is
  what makes the two drivers below testable. See
  [its capability page](../capabilities/navixsmf401re.md).
- With two boards visible under `FAMILY_STM32F4`, the "Target Board" choice
  stopped being unambiguous: a choice takes the first member sourced, so adding
  a board silently moved the default everywhere a build seeds no `.config`. The
  choice now names its reference board.
- `LED_ON` / `LED_OFF` are board-layer aliases on every board now, so a sample
  can drive the LED without knowing that this one wired it active low.

### USB CDC-ACM device driver
- `hal_usb_cdc` (`NAVHAL_CONFIG_DRV_USB_CDC`, F4 only): the target enumerates as
  a USB full-speed virtual COM port on OTG_FS. Line coding, control line state,
  `Send_Break`, `ENDPOINT_HALT` with the data-toggle reset USB 2.0 §9.4.5
  requires, and SERIAL_STATE notifications. Requires the PLL Q output at exactly
  48 MHz; `hal_usb_cdc_init()` refuses otherwise rather than enumerating at the
  wrong rate. Measured at ~275 KiB/s echo round-trip.
- Sample `34_hal_usb_cdc`; host-side checks in `tools/hil/usb_cdc_check.py`.

### RTC driver
- `hal_rtc` (`NAVHAL_CONFIG_DRV_RTC`, F4 only): calendar in the backup domain,
  alarm A, the periodic wakeup timer, and the 20 backup registers. Runs from the
  board's 32.768 kHz crystal when one is fitted, otherwise the internal RC;
  `hal_rtc_get_clock()` reports which, and the LSE wait is configurable because
  a real crystal can take seconds to start.
- Sample `35_hal_rtc`; 14 device-free on-target cases in `tests/cap/rtc/`.

### Vector table fix
- `Default_Handler` carried no `.thumb_func` / `%function` marking, so every
  `.word Default_Handler` in both vector tables held an even address. Any IRQ
  routed to the generic fallback vectored with the Thumb bit clear and escalated
  to a HardFault (`CFSR.INVSTATE`) instead of reaching
  `hal_irq_default_dispatch` — the peripheral simply looked dead. Only
  peripherals with a hand-written `<PERIPH>_IRQHandler` were unaffected, which
  is why it survived until a driver leaned on the attach-a-callback path.
- `test_vector_table_entries_are_thumb` now scans the live table so it cannot
  come back.

### Test tiers
- `tests/cap/usb_cdc/` — 15 device-free cases covering what the driver does with
  no host on the bus. Enabled in the F401 PIL config, so they run in Renode.
- `ntest hil` gained a `CONSOLE=swd` backend for boards with no serial console:
  it flashes over SWD and reads the console strings out of the target with a
  breakpoint on the console write.
- The capability contract gained a fourth scenario — an opt-in driver must be
  *absent* by default and *present* once selected, so a dead Kconfig-to-CMake
  wire cannot pass for a driver that is merely off.
